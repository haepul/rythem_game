# 캐릭터 연결 계약 — DAY 14

2026-11-10 KST. **설계 문서이며 캐릭터 구현을 시작하지 않았다.** 예시는 모두 임시 데이터다.

## 현재 코드의 책임

| 실제 모듈 | 현재 역할 | 향후 연결 지점 |
|---|---|---|
| `gacha/cards.mjs` | 6개 영구 `id`, `rarity`, `placeholderArtKey` | 추첨용 정체성 유지 |
| `draw-config.mjs` | 엄격한 카드 필드 검증, 풀/확률, 배너→설정 버전 | 새 ID를 명시적으로 풀에 등록 |
| `details.mjs` | 동일 설정에서 희귀도/개별 확률 계산 | 이름은 보조 표시, ID/확률 대응 유지 |
| `result-view.mjs:createResultCard` | 결과·보관함 공통 카드 DOM, 현재 기하학 ◇ | 이름·이미지·대체 텍스트 표시를 연결할 실제 공통 함수 |
| `card-reveal.mjs:createCardRevealView` | 재사용 카드 1장, 순서/희귀도 공개 | 같은 표시 메타데이터 조회 함수 사용 |
| `exchange-view.mjs` | 설정 카드 ID·희귀도·비용 버튼 | 이름/미리보기만 추가, 요청은 ID 유지 |
| `result-model.mjs` / `inventory-model.mjs` | 확정 이력 기반 NEW/수량 | 표시 데이터에 의존하지 않는 순수 모델 유지 |
| `acquisition-history.mjs` | 추첨/교환 합친 확정 거래 순서 | 획득 순서의 유일한 기준 유지 |

`validateDrawConfig()`는 카드 필드를 정확히 `id, rarity, placeholderArtKey`로 제한한다. **CARDS에 name/image를 바로 추가하면 설정 검증이 실패한다.** 별도 표시 레지스트리(예: 아직 존재하지 않는 `card-display.mjs`)를 제안한다. 이는 구현 완료 파일이 아니다.

```js
// 제안된 표시 전용 데이터. 실제 자산은 아직 없다.
const displays = {
  'test-card-001': {
    displayName: '임시 카드 001',
    imageUrl: null,
    alt: '민트색 마름모 임시 카드',
    placeholderArtKey: 'mint-diamond'
  }
};
```

이름/URL/대체 텍스트는 지갑이나 receipt에 복사하지 않는다. 텍스트는 `textContent`로 넣는다. 이미지 경로는 모듈 기준 `new URL('./assets/...', import.meta.url)` 등 하위 경로에 안전한 방식을 사용한다. 루트 `/assets/`를 가정하지 않는다.

## 누락·폐기 데이터

현재 UI는 이미지 네트워크 요청 없이 자체 ◇ 도형과 저장된 ID·희귀도를 표시한다. 카탈로그에서 사라진 ID도 결과/보관함에서 표시할 수 있다. `revealTheme()`의 알 수 없는 희귀도는 중립 테마이며, 정상 저장 검증은 R2/R3/R4만 허용한다.

향후 이미지가 없거나 로딩 실패하면 기존 도형으로 한 번만 대체한다. 반복 onerror 요청, 결과 지연, 재추첨은 금지한다. 장식 이미지는 빈 alt, 정보 이미지에는 의미 있는 alt를 사용하되 인접 카드명/희귀도와 중복 낭독하지 않도록 실제 스크린리더로 검증한다. 현재 `placeholderArtKey`는 추첨 검증용 필드지만 공통 카드 DOM은 아직 키별 그림을 조회하지 않는다.

## 영구 ID와 명시적 전환

- 기존 test-card ID를 실캐릭터 의미로 몰래 재사용하지 않는다. 기본 정책은 임시 카드를 보존하고 새로운 영구 ID를 발급하는 것이다.
- 표시명/자산 변경만 허용되는 경우에도 같은 카드 정체성인지 검토하고 변경 기록을 남긴다.
- ID 치환이 반드시 필요하면 별도 승인된 버전별 1:1 매핑과 새 스키마 마이그레이션을 설계한다. 병합/분할 ID는 단순 이름 교체가 아니므로 별도 정책 없이는 거부한다.
- 현재 schema 3의 엄격한 검증기를 먼저 확장하고, 공통 Web Lock 안에서 최신 원본 검증→매핑→전체 스냅샷 검증→한 번 저장한다. 쓰기 실패 시 원본 보존, 같은 버전 재실행은 무변경이어야 한다.
- receipts의 requestId, 결과 위치/중복, 확정 순서, 과거 비용·확률 설정 fingerprint와 exchanges의 정책/비용 증거를 훼손하지 않는다. 과거 요청의 fingerprint를 현재 설정으로 재작성하면 재시도 동일성 검사가 깨진다.
- 저장 결과 ID를 일괄 수정하는 정책보다, 원본 거래를 보존하는 명시적 별칭/정체성 해석 계약을 우선 검토한다. 현재 코드에는 별칭 지원이 없으며 NEW와 보관함도 원본 ID 기준이다.

## 과거 NEW 및 획득 보존

현재 `transactions` 배열이 확정 순서다. timestamp로 정렬하지 않는다. `acquisitions(wallet)`를 통해 대상 draw 이전의 추첨/교환만 읽어 NEW를 판단하며, 같은 10회 안의 두 번째 동일 카드는 NEW가 아니다. 이후 교환/추첨이 추가돼도 과거 NEW는 바뀌지 않는다. 보관함 수량은 이력에서 계산하고 별도 집계 사본을 저장하지 않는다.

새 획득 경로를 도입하면 이 순서 계약·검증기·마이그레이션·NEW 테스트를 함께 갱신해야 한다. 이미지 교체가 수량이나 NEW를 바꾸는 일은 없어야 한다.

## 새 카드/배너/교환 설정

1. CARDS에 새 고유 ID와 희귀도를 등록한다.
2. 새로운 불변 `DRAW_CONFIGS` 버전을 만들고 배너 binding을 명시적으로 바꾼다. 기존 버전/receipt는 보존한다.
3. 정수 basis points 합계 10000 및 같은 희귀도 내 균등 규칙을 검증한다. 카드 수 증가 시 카드별 확률이 달라지므로 안내도 같은 설정에서 갱신한다.
4. 교환은 별도 `REWARD_RULES`의 대상 카드/배너/비용이다. 추첨 풀 추가만으로 자동 교환 대상이 되지 않는다.
5. 이미 사용한 보너스 규칙 버전을 수정하지 않는다. `LEGACY_REWARD_VERSION`은 최초 정책으로 고정한다.
6. 확인 중 설정 변경은 기존 config-changed 경로로 재확인을 요구한다.

## 자산 도입 전 체크리스트

- 저작권/라이선스/출처/허용 플랫폼/수정 허용 범위를 자산 대장에 기록한다. 공식 게임 리소스를 복사하지 않는다.
- 프로젝트 제안 예산: 썸네일 256~384px, 큰 카드 768px 이내, 이미지당 150KB 목표. 이는 현재 측정/강제 제한이 아니라 도입 시 합의할 예산이다.
- WebP/AVIF 및 필요한 fallback, width/height/aspect-ratio로 레이아웃 이동 방지, 결과 10장 decode 비용 측정, 보관함 lazy loading을 검증한다.
- 360px/DPR2, 가로 화면, 느린 네트워크/오프라인/404, 긴 이름, alt, reduced-motion, 브라우저200% 및 Android/iOS 실기기 검증을 수행한다.
- 이미지 preload 실패가 확정 결과/건너뛰기/복귀를 막으면 출시하지 않는다. RAF/추첨 RNG/지갑 쓰기와 자산 로딩을 결합하지 않는다.

## 3주 차 제안 (미실행)

권리와 ID 정책 합의 → 표시 레지스트리와 fallback 구현 → 승인된 소수 자산 시범 연결 → 모바일 로딩/접근성/과거 저장 회귀 → 검증 후 별도 배포 승인 순서다. 실제 캐릭터·스토리·스킬, 결제·광고·현금성 보상은 이번 작업에 없다.
